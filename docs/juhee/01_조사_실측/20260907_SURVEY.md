### 🔴 선행 조건 1건 — 실물 카메라 메시지가 지금 **전건 버려진다** (검증됨)

**디바이스는 `timestamp` 를 float 로 보내고, 스키마는 `str` 을 요구한다.**

| | 값 | 근거 |
|---|---|---|
| 발행 | `"timestamp": time.time()` → **float** | `OpenMV/scripts/wash_detector.py:111,123` · `cure_detector.py:112,124` |
| 스키마 | `timestamp: str` | `web-api/app/vision/schemas.py:38` (heartbeat 도 동일 `:44-51`) |

실제로 돌려서 확인했다 (`web-api/venv/bin/python`, pydantic **2.13.5**):
`MQTTStatusMessage(**payload)` → `ValidationError: timestamp — Input should be a valid string
[input_type=float]`.

경로는 이렇다 — `mqtt_client.py:126` 에서 예외가 나고 `mqtt_client.py:86-88` 의
`except Exception` 이 잡아 `logger.error("MQTT 메시지 처리 오류: ...")` 로 흘린다.
⇒ **상태 갱신이 일어나지 않고 메시지가 사라진다.** 로그는 남지만 조용히 실패하는 쪽에 가깝다.

🚨🚨 **그리고 시뮬레이터는 통과한다** — `web-api/app/vision/simulator.py:74` 가
`now.isoformat()`(str)을 보낸다.
⇒ ⭐⭐ **"시뮬은 되고 실물만 안 되는" 형태**이고, 이것은 아래 「목표 라인 vs 현행 라인」과
**정확히 같은 계열의 결함**이다. 이번 조사에서 그 형태를 **두 군데서 찾았다.**

**대응** = `timestamp` 를 `float | str` 로 받거나 발행 측을 `isoformat()` 으로 맞춘다.
🟡 **어느 쪽이 맞는지는 [미확인]** — 실물 카메라가 지금 현장에서 도는지 확인이 필요하다
(돌고 있는데도 아무도 몰랐다면 vision 상태감시가 **실질 미가동**이라는 뜻이다).
⇒ **P4 착수 전 첫 확인 항목.**

**영향** D4 와 함께 본다. M2a 매핑 작업량은 지시서 예상보다 작지만, **선행 버그 1건이 앞에 있다.**

## 🚨 목표 라인 vs 현행 라인 — 그대로 두면 실물 `MOVED` 가 전건 거부된다

**전제 확정** — `topology.yaml` §2.3 = **10월 재배치 후 목표 라인**. 코드 = **현행 라인**.
⇒ 두 개가 다른 것 자체는 위반이 아니다. **문제는 그 다음이다.**

`docs/juhee/state_engine.py:179-185` 의 `_moved()` 는 이동을 **`route` 로 검증**하고,
없으면 `ValueError("토폴로지에 없는 이동")` 을 던진다.

현행 실물 이동은 이렇다 (`sequence_service/app/cell/sequences/robot.py:212-300`):

| task | 실제 이동 | 목표 route 에 있나 |
|---|---|---|
| `SW` / `P` | 프린터 → 세척기 | 🟡 중간에 완료 랙이 끼어 있어 직접 엣지가 없다 |
| **`FW`** | **세척기 → 빈 프린터에 되주차 → 경화 대기** (`:234-270`, 로그 원문 `wash->{printer}->cure`) | 🔴 **없다** |
| `SC` | → 경화기 (`:277-289`, 오늘은 흔히 생략) | 🟡 |
| `FC` | 경화기 → 반출 (`:290-300`) | 🟡 완료 랙 경유가 없다 |

목표 route(`topology.yaml:127-135`)에는 `WSH-0x → PRT-0x` 엣지가 **없다.**

> ⇒ 🔴 **P4/P5 에서 실물 `MOVED` 를 흘리면 셀A 이동이 전건 예외로 죽는다.**
> 🚨 **시뮬레이터로는 절대 드러나지 않는다** — 시뮬은 목표 라인만 밟기 때문이다.
> **P2 완료 기준을 통과해도 P5 에서 처음 터지는 종류**다.

**대응 = 설계에 이미 이음매가 있다.** §2.2-8 이 `route`/`unit` 에 `line_id` 를 미리 넣어둔 것의
**첫 실제 용도**가 이것이다.

| 항목 | 처리 |
|---|---|
| 현행 라인 | `line_id = RESIN-1-ASIS` 로 **함께 등록**. 되주차 엣지 포함, 완료 랙 없음 |
| 목표 라인 | `line_id = RESIN-1` 그대로. 재배치 후 신규 `unit` 을 이쪽으로 발급 |
| 경화기 2호기 | 목표엔 2대 유지, 현행은 `node.is_active = false` — **`is_active` 를 둔 이유가 이것** |
| 전환 | route 재작성이 아니라 `unit.line_id` 발급 대상만 바뀐다. 진행 중 제품은 옛 라인으로 완주 |

### 🔴 그런데 `topo_sync.py` 가 그 이음매를 지원하지 않는다 (레퍼런스 결함 2건)

`expand_routes`(`topo_sync.py:64`)·`expand_spans`(`:82` `adj[(line_id, f)]`)·DB 스키마는
**라인을 구분한다.** 그런데 **게이트 1·2 만 `line_id` 를 버린다.**

| 결함 | 근거 | 결과 |
|---|---|---|
| **게이트 1(순환)이 전 라인을 한 그래프로 합친다** | `topo_sync.py:144-146` — `adj[f].append(t)` / `indeg[t] += 1` 에 `line_id` 가 없다. 판정은 `:157` `visited < len(node_ids)` | 두 라인이 노드를 공유하므로 **사이클이 없어도 있다고 나온다**: 목표 `PRT-01→RK-PRT-DONE→WSH-01` + 현행 `WSH-01→PRT-01` = 합친 그래프에서 순환 |
| **게이트 2(고립)도 합친다** | `topo_sync.py:161` — `used` 가 라인 무관 | 한 라인에만 연결된 노드를 고립으로 잡지 못한다(느슨한 쪽 오류) |

⇒ **두 라인 병행은 `topo_sync.py` 를 먼저 고쳐야 성립한다.**
수정은 작다 — `adj`/`indeg`/`used` 의 키를 `(line_id, node)` 로 바꾸고 **라인별로 Kahn 을 돌린다.**
🥇 **P1 의 첫 작업이 이것이고, 이것 없이는 D1·D2 답이 무엇이든 P5 에서 막힌다.**

🟡 **되주차 자체가 진짜 사이클**(`PRT → WSH → PRT`)이므로, 라인별로 고쳐도 **현행 라인은 여전히 거부된다.**
`v_node_order` 재귀 CTE 도 `depth < 50` 가드로 죽지는 않지만 `step_order` 가 뒤섞인다.
⇒ **갈림길** = 되주차를 route 엣지로 볼 것인가, "프린터를 임시 보관 슬롯으로 쓰는 것"으로 볼 것인가.
후자면 사이클이 사라진다. ⇒ **D6.**

## 게이트 답변 초안

**D1 — `sequence_service` 를 개조한다. 단 2단계로 나눈다.**
이미 M3b 이므로 별도 M3b 는 배정 로직 이중화를 만든다. 그러나 `PostProcStage` / `mainSequence.py`
하드코딩을 `route` 조회로 바꾸는 것은 **운영 중인 로봇 제어 코드 개조**이고, 틀리면 라인이 선다.
- ① `robot.py:204 _complete_task` 에서 **`contract.Moved` 를 발행만 추가** — 관측 전용, 제어 무변경.
  실패해도 반송이 멈추지 않도록 예외를 삼킨다(8/7 *"웹 전송 실패가 인식을 멈추지 않는다"* 원칙과 동일).
- ② `route` 이관은 **대시보드가 실물 데이터로 검증된 뒤**.

**D2 — 별도 PostgreSQL. 기존 데이터는 이관하지 않고 병행 기록한다.**
SQLite 는 `timestamptz` 가 없고 재귀 CTE 뷰를 쓰기 나쁘며, MariaDB 는 **로봇이 돌고 있는 DB** 라
스키마를 건드리면 라인이 선다. Grafana 는 PostgreSQL 을 1급으로 다룬다.
🚨 **이관 불가 사유는 용량이 아니라 층위다** — `print_command`(잡) ↔ `unit`(개체) 1:1 매핑이 없다.
설치 위치는 S7 이 미결이므로 **D2 안에서 함께 정한다.**

**D3 — 로봇이 세우는 완료 비트 = `레지스터 206`(Robot Moved) 을 폴링하는 현행 방식 그대로.**
확인 지점은 `robot.py:578-598 STEP0070`, 발행 지점은 `robot.py:204 _complete_task` 이고
`RobotTask.from_unit`/`to_unit` 로 from→to 귀속이 된다. **별도 센서 불필요.**
🚨 **150/151 은 완료 신호가 아니다** — 둘 다 **PC→로봇 송신 트리거·PC Ready** 다
(초안 작성 중 내가 이 둘을 완료 신호로 적었고, `config.py:39-42` 를 열어 정정했다).
ARM-B(빔피킹) 구간은 Modbus 가 아니라 소켓 경로이므로 `MOVED` 를 **따로** 만들어야 한다.

**D4 — 프린터 API 를 1차 정보원으로.**
폴링이 이미 15초로 돌고 있고 **프린터에는 카메라가 아예 없다** ⇒ 경쟁 관계가 아니므로
지시서가 검토하라 한 *"카메라 강등"* 은 **불필요**. `source='ADAPTER'`.
카메라는 wash/cure 의 유일한 정보원이므로 그대로 1차다.

**D5 — 기존 프론트엔드 존치.**
조작 기능이 4탭(`print`/`queue`/`automation`/`automation_manual`)에 있어 Grafana 가 대체 못 한다.
대상도 다르다(프린터 대수 상태 vs 제품 개체 통과 현황).

**🆕 D6 (조사에서 새로 필요해진 결정) — 현행 라인의 "세척 → 빈 프린터 되주차"를
route 엣지로 볼 것인가, 임시 보관으로 볼 것인가.**
- 엣지로 보면 route 에 사이클이 생겨 `topo_sync` 게이트 1 이 현행 라인을 **거부**한다.
- 임시 보관으로 보면 사이클이 사라지지만, `MOVED` 두 번(`WSH→PRT`, `PRT→CUR`)을
  어떻게 기록할지 정해야 한다.
🚨 **P1 착수 전에 답이 필요하다.**

## 사업 맥락 리스크 2건

1. **산출물 ⑤ 「클라우드 Lite MES/ATS 대시보드」는 위탁2 범위(프론트엔드 구현)다.**
   Grafana 를 우리가 직접 만드는 것이 위탁 범위와 **중복인지 확인이 필요하다.**
   중복이면 위탁 과업을 재정의하고, 아니면 **Grafana = 내부 관측 / 위탁2 = 대외 대시보드**로
   층위를 나눠 둘 다 살린다.
2. **협약 종료가 2026-10-31 이고, 현재 최우선 과제는 빈피킹 파지다.**
   Phase 0~5 전체 + PostgreSQL 신규 도입은 그 우선순위와 경쟁한다.
   ⇒ 판단 근거: **P1(토폴로지) + P2(시뮬) + P3(Grafana) 는 운영 코드를 건드리지 않아 병행 가능**하고,
   **P5(반송 제어)만 물리적 위험이 있다.** 즉 P3 까지는 빈피킹과 부딪히지 않는다.
   🚨 단 위 「목표 vs 현행 라인」 문제 때문에 **P3 까지 통과해도 P5 성공이 보장되지 않는다** —
   이 점을 일정 판단에 반영해야 한다.
