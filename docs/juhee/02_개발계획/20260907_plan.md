## 1. 절대 규칙

| 규칙 | 이유 |
|---|---|

## 2. 목표 아키텍처 (설계 확정분)

### 2.1 모듈 분할

| 모듈 | 책임 | 이 저장소의 후보 |
|---|---|---|
| **M1** 토폴로지 | `topology.yaml` → DB 동기화. 설비/랙/경로/반송자원 정의 | 신규 |
| **M2a** MQTT 어댑터 | 카메라 추론 → `STATE` 이벤트 | `web-api/app/vision/mqtt_client.py` ← **확인 필요** |
| **M2b** Modbus 어댑터 | 로봇암 지시/완료 → `MOVED` 이벤트 | `bin_picking/src/communication/modbus_server.py` ← **확인 필요** |
| **M3a** 상태 엔진 | 이벤트 소비 → `product_state` 갱신, `display_id` 채번 | 신규 (일부는 `automation_db` 와 중복 가능) |
| **M3b** 반송 제어기 | 이동 후보 산출 → 반송 자원 배정 → 지시 발행 | `sequence_service/` ← **가장 큰 중복 위험** |
| **M4** 조회 뷰 | Grafana 전용 SQL 뷰 | 신규 |
| **M5** 대시보드 | Grafana Repeat + 라인 개요 | 신규 (`frontend/` 7탭과 역할 중복 가능) |

### 2.2 핵심 설계 결정

1. **토폴로지는 데이터다.** 설비/랙은 `node` 테이블 한 개로 통합. 랙은 "가공하지 않고
   용량이 큰 노드". 공정 순서는 `step_seq` 정수가 아니라 `route` 엣지 테이블로 표현하고
   재귀 CTE로 계산한다. 노드 제거는 `DELETE`가 아니라 `is_active=false`.

2. **위치를 확정하는 것은 반송 완료뿐이다.** 카메라는 설비 상태를 *추정*하고(confidence 동반),
   로봇암의 이동 완료만이 `product_state.node_id` 를 바꾼다. 카메라 오탐이 위치를 틀어뜨리면 안 된다.

3. **제품 ID는 UUID(불변) + display_id(가변) 분리.** `P3-W2-C5` 는 공정마다 값이 바뀌는
   라벨이므로 식별자로 쓸 수 없다. `unit_alias` 로 과거 이름도 검색된다. 순번은 리셋하지 않는다.

4. **채번은 반송 확정 후에만.** 카메라가 "끝난 것 같다"고 할 때 미리 번호를 따면
   반송 실패 시 번호가 새고 순번이 실제 처리 순서와 어긋난다. 채번 지점은 M3a 단 한 곳.

5. **건조/냉각은 상태가 아니라 `ready_at` 필드다.** `SETTLING` 을 상태로 두면 M3a에
   타이머와 재기동 복구 로직이 생긴다. `ready_at` 은 뷰에서 파생 표시하고, 나중에 온도 센서로
   바꿔도 M3b는 안 바뀐다.

6. **관측 경로와 제어 경로를 분리한다.** M3a는 DB만 쓰고 로봇에 명령하지 않는다.
   M3b가 죽어도 대시보드는 살고, M3a가 죽어도 라인은 수동으로 돈다.

7. **반송 자원은 노드가 아니다.** `transporter` + `route_handler`(엣지별 담당). YAML에는
   `span: [A, B]` 로 선언하고 동기화 시 엣지로 펼친다. 한 엣지에 담당자는 하나(PK 제약).

8. **FDM 대비 이음매를 미리 만든다.** `node_type` 은 enum/CHECK 가 아니라 테이블.
   `route`/`unit` 에 `line_id` 컬럼(P0에서는 라인 1개만 운영).

### 2.3 현재 라인 구성

```
프린터 대기 랙 → 프린터 ×4 → 프린터 완료 랙 → 세척기 ×2 → 세척기 완료 랙
  → 경화기 ×2 → 치수검사 → 빔피킹 대기 랙(트레이) → 빔피킹/드릴링/트림 → 완료 랙
```

노드 15, 엣지 19. 반송 담당은 **ARM-A 12 / OP-CURE(수동) 5 / ARM-B 2**.
빔피킹 대기 랙만 트레이 단위(트레이 ID·수량만 추적, 셀 좌표는 추적하지 않음).

### 2.4 참조 산출물

설계 검증용 레퍼런스 구현이 있습니다. **그대로 복사하지 말고, 조사 결과에 맞춰 통합하세요.**

- `topology.yaml` — 토폴로지 정의
- `schema.sql` — DDL 전체 + 뷰 4개
- `topo_sync.py` — 동기화 CLI, 6개 검증 게이트
- `contract.py` — M2↔M3a 이벤트 계약 (SPAWN / STATE / MOVED)
- `state_engine.py` — M3a 레퍼런스
- `simulator.py` — 설비 없이 라인 구동

## 3. Phase 0 — 조사 (읽기 전용)

각 과제마다 **알아낼 것**과 **판정**을 `SURVEY.md` 에 기록합니다.
판정은 반드시 `재사용` / `수정` / `신규` / `제거후보` / `보류` 중 하나입니다.

### S1. 기존 DB 실체 파악 ★최우선

**대상**
```
web-api/app/local/automation_db.py
web-api/app/models/
web-api/app/binpick/models.py
sequence_service/app/db/
```

**알아낼 것**
- DBMS가 무엇인가? (PostgreSQL / SQLite / MSSQL / 파일)
- 실제 테이블 목록과 행 수. 운영 중 데이터가 얼마나 쌓여 있나
- **제품 개체를 추적하는 테이블이 이미 있는가?** 있다면 PK가 무엇인가
- `P3-W2-C5` 형태의 ID가 이미 어딘가에 저장되고 있는가
- 설비 목록이 테이블에 있는가, 코드 상수인가, 설정 파일인가
- 마이그레이션 도구(alembic 등)를 쓰는가

**조사 힌트**
```bash
rg -n "CREATE TABLE|Base.metadata|declarative_base|__tablename__" web-api sequence_service
rg -n "sqlite|postgresql|pyodbc|psycopg|create_engine" --type py -g '!kaist_backup'
rg -n "P\d+-W\d+|display_id|product_id|part_id" -g '!kaist_backup' -g '!yolo_track'
find . -name "*.db" -o -name "*.sqlite*" -not -path "./kaist_backup/*"
```

**판정 기준**
- 기존 테이블에 제품 이력이 쌓여 있다 → 새 스키마와 **병행 운영 후 이관**. 매핑표를 만든다
- 설비 목록이 코드 상수다 → **M1로 이관 대상**. 상수를 쓰는 지점을 전부 목록화
- DBMS가 PostgreSQL이 아니다 → 게이트 D2에서 결정 필요

### S2. MQTT 경로 — M2a 후보

**대상**
```
web-api/app/vision/mqtt_client.py
web-api/app/vision/camera_manager.py
web-api/app/vision/routes.py
web-api/app/vision/simulator.py
web-api/app/mosquitto/config/
```

**알아낼 것**
- 토픽 구조와 페이로드 스키마. 실제 샘플 메시지를 하나 확보할 것
- **설비 식별자를 어떻게 싣는가?** 우리 `node_id` 체계(`PRT-01`)와 매핑 가능한가
- 추론 신뢰도(confidence)가 페이로드에 있는가
- **디바운싱이 이미 있는가?** 없으면 프레임 단위로 상태가 튄다
- 메시지를 받아서 지금 무엇을 하는가 (DB 저장? 웹소켓 푸시? 둘 다?)
- `vision/simulator.py` 가 무엇을 시뮬레이션하는가 — 우리 `simulator.py` 와 겹치는가

**판정 기준**
- 토픽/페이로드가 이미 설비 상태를 싣는다 → **재사용**. `contract.State` 로 변환하는 얇은 매퍼만 추가
- 페이로드에 confidence가 없다 → 카메라 측 수정 필요. 없으면 `NULL` 로 두고 디바운싱만
- 디바운싱이 없다 → **어댑터에 추가**(M3a가 아니라 M2a 책임)

### S3. Modbus / 로봇 경로 — M2b 후보 ★설계 전제 확인

**대상**
```
bin_picking/src/communication/modbus_server.py
bin_picking/src/communication/pick_socket_server.py
bin_picking/src/communication/web_reporter.py
bin_picking/src/communication/grasp_plan.py
bin_picking/scripts/rodi_pick_sequence.js
bin_picking/scripts/rodi_iomap_minimal.js
bin_picking/tests/simulate_rodi_pick.js
```

**알아낼 것**
- **마스터/슬레이브 방향.** 파일명이 `modbus_server` 이므로 우리 쪽이 슬레이브(레지스터 제공)이고
  로봇이 폴링해 갈 가능성이 높다. 이는 "우리가 로봇에 지시를 보낸다"는 설계 전제와 다르다
- 레지스터 맵. 어떤 주소에 무엇이 들어가나
- 이동 **완료** 신호가 존재하는가? 있다면 어떤 형태인가 (레지스터 비트 / 소켓 / 웹 리포트)
- 이동 완료가 어느 노드→어느 노드인지 식별 가능한가
- `pick_socket_server` 와 `modbus_server` 의 역할 차이
- 이 경로가 지금 **빔피킹(ARM-B) 전용인가?** ARM-A(프린터~세척 구간)는 별개 경로인가

**판정 기준**
- 슬레이브 방향이 맞다 → M3b는 "레지스터에 다음 지시를 써 두는" 방식으로 설계 변경.
  이 경우 `MOVED` 이벤트는 로봇이 완료 비트를 세운 것을 **폴링해서** 만든다
- ARM-A 경로가 없다 → **신규**. ARM-A는 12개 엣지를 담당하는 병목이므로 우선순위 높음
- 완료 신호가 없다 → **설계 위험**. 위치 확정 근거가 사라진다. 게이트 D3

### S4. 시퀀스 런타임 — M3b 중복 위험 ★

**대상**
```
sequence_service/app/cell/
sequence_service/app/core/
sequence_service/app/io/
sequence_service/app/main.py
docs/hansol_handover/
```

**알아낼 것**
- **이미 반송 오케스트레이션을 하는가?** "어느 제품을 어디로 옮길지" 결정 로직이 있는가
- 공정 순서가 어디에 정의돼 있는가 (하드코딩? 설정? 상태머신?)
- 설비 개수가 코드에 박혀 있는가
- `io/` 가 무엇과 통신하는가 (아진 IO? PLC?)
- `web-api/app/local/ajin_io.py` 와의 관계

**판정 기준**
- 이미 오케스트레이션을 한다 → **M3b를 새로 만들지 않는다.** `sequence_service` 가
  이동 완료 시 `contract.Moved` 를 발행하도록 **수정**하는 쪽이 옳다
- 공정 순서가 하드코딩돼 있다 → M1의 `route` 를 읽도록 **수정**. 이것이 설비 증감 대응의 핵심
- 완전히 별개 관심사다 → 그대로 두고 M3b 신규

### S5. 프린터 어댑터 — M2 패턴 선례

**대상**
```
web-api/app/adapters/base.py
web-api/app/adapters/factory.py
web-api/app/services/formlabs_client.py
web-api/app/services/polling_service.py
web-api/app/local/preform_client.py
```

**알아낼 것**
- 어댑터 인터페이스가 무엇을 추상화하는가
- **설비 인스턴스를 어떻게 열거하는가?** 설정 파일인가 DB인가 상수인가
- 프린터 상태(출력중/완료)를 이미 폴링하고 있는가 — 그렇다면 카메라와 **정보원이 중복**
- 새 프린터 추가 시 코드 수정이 필요한 구조인가

**판정 기준**
- 기존 어댑터 패턴이 우리 M2 계약과 호환된다 → **패턴을 따른다.** 새 추상화를 만들지 않는다
- 프린터 상태를 이미 API로 안다 → 카메라보다 신뢰도 높음. `source='ADAPTER'` 로 우선 채택하고
  카메라는 보조로 강등하는 것을 검토 (게이트 D4)

### S6. 프론트엔드 vs Grafana — 역할 경계

**대상**
```
frontend/src/components/   (7탭 + 모달)
frontend/src/services/api.ts, localApi.ts
web-api/app/api/routes.py
```

**알아낼 것**
- 7개 탭이 각각 무엇을 보여주는가. 목록화할 것
- 그중 **공정 현황 모니터링**에 해당하는 탭이 있는가
- 실시간 갱신 방식 (폴링? 웹소켓?)
- 조작 기능이 있는가 (버튼으로 설비 제어 등)

**판정 기준**
- 모니터링 탭이 이미 있다 → Grafana와 **중복**. 게이트 D5에서 존치/이관 결정
- 조작 기능이 섞여 있다 → Grafana는 조작을 못 하므로 그 탭은 **존치**

| **D2** | 새 스키마를 **어느 DB에** 올릴 것인가. 기존 DB와 같은 인스턴스인가 별도 PostgreSQL인가. 기존 데이터를 이관할 것인가 | S1, S7 |

| **D4** | 프린터 상태의 **1차 정보원**을 카메라로 할 것인가 프린터 API로 할 것인가 | S2, S5 |
| **D5** | 기존 프론트엔드 모니터링 탭을 **존치**할 것인가 Grafana로 이관할 것인가 | S6 |

## 5. Phase 1~5 (게이트 통과 후)

각 Phase는 **완료 기준을 눈으로 확인할 수 있어야** 합니다.

### P1 — M1 토폴로지 도입
- **추가** `config/topology.yaml`, `tools/topo_sync.py`, DDL
- **수정** S1/S4에서 찾은 설비 목록 하드코딩 지점 → DB 조회로 교체
- **완료 기준** `topo_sync --apply` 후 재고 있는 랙을 YAML에서 지우면 **거부**될 것

### P2 — M3a 상태 엔진 + 시뮬레이터
- **추가** `contract.py`, `state_engine.py`, `simulator.py`
- **수정** 기존 제품 추적 로직이 있다면 이관 경로 마련 (병행 기록)
- **완료 기준** 설비·로봇 없이 제품이 완주하고 `display_id` 가 `P1-W1-C1-B1` 로 누적

### P3 — M5a Grafana Repeat 대시보드
- **추가** 뷰 4개, Grafana provisioning, `$node` 변수 + Repeat 패널
- **완료 기준** YAML에 프린터 2대 추가 후 `--apply` → 카드가 **자동으로 6장**

### P4 — M2a MQTT 어댑터 실물 연결
- **수정** `vision/mqtt_client.py` → `contract.State` 발행 (디바운싱 포함)
- **제거 후보** `vision/simulator.py` 중 P2 시뮬레이터와 겹치는 부분
- **완료 기준** 프린터만 실물, 나머지는 시뮬로 **병행 운영**

### P5 — M2b Modbus + M3b 반송 제어
- **수정** D1/D3 결정에 따름
- **완료 기준** dry-run(지시 계산만) → 1개 구간 실발행 → 전 구간. 물리적 위험이 있는 유일한 단계
