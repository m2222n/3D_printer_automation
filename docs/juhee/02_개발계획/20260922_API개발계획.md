## 3. 스택 결정 — **SQLAlchemy 를 쓰지 않는다**

명세 B-5 는 *"읽기 SQLAlchemy Core + 쓰기 psycopg"* 를 그렸고, 그래서 §10-7 에 🔴**"`conn.transaction()` 이 SQLAlchemy 트랜잭션 안에서 세이브포인트로 도는지 미검증"** 이 열려 있다.

| 안 | 내용 | 판정 |
|---|---|---|
| B-5 원안 | 읽기 SQLAlchemy · 쓰기 psycopg | 🔴 라이브러리 2개 · 커넥션 수명 2벌 · **§10-7 을 시험해야 한다** |
| 🥇 **psycopg3 단독** | `psycopg_pool.ConnectionPool` + `row_factory=dict_row` · 읽기는 `SELECT`, 쓰기는 같은 커넥션을 `StateEngine(conn)` 에 넘긴다 | 🟢 **§10-7 이 시험 없이 닫힌다**(경계가 없다) · 읽기 코드가 더 짧다(`cur.execute` → dict 리스트 → pydantic) |

✅ **psycopg3 단독 채택.** 근거 = ①`StateEngine` 이 이미 psycopg3 API(`with conn.transaction():`)로 쓰여 있고 **그 파일을 안 고치는 것이 가장 싸다** ②v2 는 뷰만 읽으므로 ORM 이 할 일이 없다(모델 0개) ③W1·W4 의 한 트랜잭션이 psycopg 안에서 그냥 성립한다.

⚠️ **기존 v1 의 SQLAlchemy(SQLite·MariaDB)는 그대로 둔다.** 이 결정은 v2 커넥션에만 적용된다.

```python
# app/line/db.py — 이 파일이 전부다
POOL = ConnectionPool(settings.DATABASE_URL_LINE, min_size=1, max_size=4,
                      kwargs={"row_factory": dict_row}, open=False)

def rows(sql: str, **p) -> list[dict]:
    with POOL.connection() as c:
        return c.execute(sql, p).fetchall()
```

⇒ **읽기 엔드포인트 하나 = 5줄**(SQL 한 줄 + `response_model` 한 줄). 리포지토리 클래스·서비스 계층을 만들지 않는다.

## 5. ~~🔴~~ ✅ 뷰 ↔ FE 계약이 어긋난 자리 8개 (이 계획의 본체) — **9/23 전부 반영**(1·2·3·4·6·7 = schema.sql 뷰 · 5·8 = API AS/조인 · checkLineApi 구조 단정)

FE 타입은 명세 + schema.sql 을 보고 썼는데, **뷰가 실제로 내보내는 컬럼과 다른 곳이 8군데** 있다. 실측으로 확인했다.

| # | 엔드포인트 | 뷰가 내는 것 | FE 가 받는 것 | 메우는 방법 |
|---|---|---|---|---|
| 1 | R1 | `display_ids` = **`'A, B, C'` 콤마 텍스트** | `string[]` | 🥇 **뷰에서 `string_agg`→`array_agg`** (API 파서를 만들지 않는다) |
| 2 | R1 | **`attrs` 컬럼이 없다.** `splits_batch`·`count_by_group` 불리언만 | `attrs: {measure, duration_input, …}` | 뷰에 **`n.attrs` 한 컬럼 추가** (실측 = `INS-01` 만 `{"measure":{key,label,unit}}` 보유) |
| 3 | R1·R7 | `v_rack_slot` = `used`·`free`·`contents` 텍스트, **`head_display_id` 없음** | `occupancy` · `head_display_id` · `contents: string[]` | 뷰에서 이름 맞추고(`used AS occupancy`) `head_display_id` = `pos_no=1` 행 · `contents` 배열화 |
| 4 | R3 | `v_wip` 에 **`waiting` 이 없다** | `waiting: boolean` | 뷰에 `node_kind='RACK'` 파생 추가 (🚨 API 가 계산하면 화면마다 갈라진다 — 명세 §7 원칙) |
| 5 | R6 | `v_rack_load` = `slot_capacity`·`unit_qty`·`slots` | `capacity`·`occupancy`·`slot_count` | 엔드포인트에서 **`AS` 로만 매핑**(계산 없음 ⇒ 뷰 추가 안 함) |
| 6 | **R9** | 🥇 `sources`·`parts` 가 **콤마 텍스트**이고 **출처별 파트 수량이 없다**(`parts` = `'PN-B-1180, PN-C-770'`) | `sources: [{parent_display_id, parts: {PN: qty}}]` | 🔴 **가장 큰 구멍.** 뷰를 `jsonb_agg(jsonb_build_object(...))` 로 고친다 — 지금 값으로는 화면이 못 그린다 |
| 7 | R10 | `nominal_mm`·`tol_mm` 두 컬럼 · **`measure_spec` 없음** | `tol: {nominal_mm, tol_mm}` · `measure_spec: {key,label,unit}` | `tol` 은 엔드포인트에서 묶고, `measure_spec` 은 뷰에 `node.attrs->'measure'` 추가 |
| 8 | R8 | 4개 조인(계산 없음) | `kinds`·`part_name`·`qty_scrapped` | `v_unit_content.kinds` · `part.name` · `unit_content.qty_scrapped` 로 **조인만** (명세대로 새 뷰 없음) |

⭐ **판정 원칙 = 계산은 뷰가, 이름 바꾸기는 API 가.** 1·2·3·4·6·7 은 뷰 수정(계산·집계), 5·8 은 API 의 `AS`·조인.
🚨 **뷰 컬럼 타입을 바꾸면 `CREATE OR REPLACE` 가 안 된다 — `DROP … CASCADE` 후 재생성**이고 의존 뷰를 먼저 확인해야 한다(명세 §10-10 이 같은 함정을 기록했다).

### 🚨 부수 발견 = FE 목업의 토폴로지가 DB 와 다르다

| | FE 목업 | 실제 DB(`RESIN-1`) |
|---|---|---|
| 제어 서브 탭 | **6개**, 첫 탭 `출력 · 세척`(node_count 6) | **7개**, 첫 탭 `프린터`(4) · 둘째 `세척기`(2) |

`frontend/scripts/checkLineApi.ts` 가 **`menu.length === 6`** 과 첫 탭 이름을 **고정값으로 단정**한다.
⇒ 📌 **실 API 로 바꾸면 이 단정이 깨진다. 고칠 쪽은 DB 가 아니라 검사다** — 개수·이름 단정을 **구조 단정**(순서 오름차순 · `node_count === node_ids.length` · `ui_kind` 비어 있지 않음)으로 바꾼다. 나머지 38건은 그대로 쓴다.

## 7. W6(로봇 명령) 은 어디까지 하나 — 🚨 정직하게 자른다

명세 §4-W6 = *"①`command_log` 기록 ②어댑터 호출 ③결과 반환"* 이고 **v2 가 Modbus·DO 를 직접 치지 않는다**(한화 = *"하나의 프로세스만 제어권을 가진다"*).

🔴 **그런데 그 "어댑터" 가 web-api 안에 없다.** 실제 송신 경로는 `bin_picking/src/communication/pick_socket_server.py`(소켓)와 `sequence_service`(Modbus)이고 **둘 다 web-api 가 부르는 구조가 아니다.**

⇒ **P4 범위 = ①`verified=false` 면 409 `UNVERIFIED_COMMAND` ②`command_log(kind='DEVICE')` 기록 ③`WriteResult.ok=false` + `warnings:["송신 어댑터 미연결"]`**
🚨 **"실행됨" 으로 응답하지 않는다.** 실제로 안 나갔는데 ok=true 를 주면 작업자가 로봇이 받은 줄 안다. 어댑터 연결은 별건(제어권 경계 결정이 선행).
