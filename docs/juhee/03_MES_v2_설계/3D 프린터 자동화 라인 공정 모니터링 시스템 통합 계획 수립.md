## 개념 13개

```
라인이 어떻게 생겼나   노드 · 칸 · 경로 · 채번 · 반송자원
무엇을 만드나          주문 · 파트 · 개체 · 내용물
지금 어디 있나         상태 · 이력
누가 무엇을 판단했나   판정 · 조작 이력
```

공정 타입(`PRINTER`, `WASHER` …)은 개념이 아니라 **노드의 라벨**이다.
동작 차이는 전부 노드 속성에서 읽는다 — `id_prefix` `post_delay_s` `slot_access` `splits_batch` `ui_kind`.

## 데이터 모델

```
customer_order   주문      고객 · 납기                  주문 : 배치 = 1 : N
      ↓
unit (BATCH)     배치      한 플레이트 분량 · P3-W2       배치 : 부품 = 1 : N
      ↓ Split (부품 분리)
unit (PART)      부품      개별 부품 · P3-W2-S15-C102

플레이트 = line.plate_count 숫자.   바구니·박스 = product_state.group_id 꼬리표.
관측 시스템은 실물을 모방하지 않는다.
```

## 설계 원칙 5가지

1. **토폴로지는 데이터다** — 설비 개수·공정 순서가 코드에 없다
2. **위치는 반송 완료로만 확정한다** — 카메라는 추정
3. **채번은 한 곳에서만** — M3a `_relocate()`. 조건 = 가공했고, 그 노드에서 아직 이름을 안 받았을 것
4. **삭제하지 않는다** — `is_active = false`
5. **관측 시스템은 실물을 모방하지 않는다** — 플레이트는 숫자, 바구니는 꼬리표

# 공정 흐름

공정 흐름 상세

**현행** `프린터 대기 랙 → 프린터×4 → 세척기×2 → 경화기×1 → 완료 랙` (되주차 포함)

**재배치 후** `… → 세척기 완료 랙 → 부품 분리 → 서포트 제거 → 경화기×2 → 치수검사 → 빔피킹 대기 랙 → 빔피킹/드릴링/트림 → 완료 랙`

- 두 라인 등록. 노드 18 · 칸 11 · 엣지 60 (ASIS 27 / RESIN-1 33). 🔄 **활성 라인은 하나만** — `RESIN-1-ASIS` `active: true` · `RESIN-1` `active: false`(9/23). `.env LINE_ID=RESIN-1-ASIS` 와 짝. 재배치 날 두 값을 맞바꾸고 `topo_sync --apply`
- **부품 분리와 서포트 제거는 논리 노드 둘, 물리 작업대는 하나.**
분리에서 배치가 부품으로 나누고(`splits_batch`), 서포트는 부품을 하나씩 다듬는다
- 반송 담당은 **노드별** `node.transporter_id`. ARM-A(프린터~세척) · OP-CURE(작업자, 분리~검사) · ARM-B(빔피킹). 폐기는 담당 없음
- 🔴 **세척기 신호는 카메라가 아니라 리모트 I/O(PET-2255U)에서 온다** — 는 **방침이고 아직 배선되지 않았다.**
🔄 지금 코드가 발행하는 세척기·경화기 `State` 는 **카메라 MQTT**(B4 · `mqtt_client.py:124` · `external_ref.mqtt`)다. 리모트 I/O 를 MQTT(M2a) 로 붙일지 Modbus TCP(M2b) 로 폴링할지는 **여전히 미결**
- 랙 = `칸 > 자리`, **FIFO 대기열**. 순번은 절대 좌표가 아니라 "앞에서 몇 번째"
- 순서 변경·랙 증설·칸 변경 전부 **YAML 2~3줄**로 검증됨
- 🔄 **외부 식별자는 `node.external_ref` jsonb** — 프린터 시리얼은 `web-api/.env PRINTER_SERIAL_MAP` 에서 `topo_sync` 가 주입, 카메라는 `mqtt: wash_1…`, 제어 DB 는 `legacy_task_unit: printer-1…`. 어댑터는 이 값으로 노드를 역조회한다

# 출력물 관리

출력물 관리 상세

추적 단위가 **서포트 제거에서 바뀐다.** 그 앞은 배치(플레이트 한 장 분량), 그 뒤는 개별 부품. 전환점은 **부품 분리**다.

|  | 배치 (BATCH) | 부품 (PART) |
| --- | --- | --- |
| 구간 | 프린터 ~ 부품 분리 | 부품 분리 이후 |
| 공정번호 | `P3-W2` 까지 | `P3-W2-S15-C102-D98-B45` — 앞부분은 배치에서 상속 |
| 파트넘버 | `unit_content` 에 파트당 수량 (혼재 2~3종) | `unit_content` 에 한 행 `qty=1` |
| 불량 | `part_scrap` 으로 수량 차감. NG 는 `unit` 이 안 생김 | `EXIT-SCRAP` 으로 이동 |
| 판정 | `judgement` — OK/NG · 측정값 | 같은 테이블. 뒤집기는 새 행 |
- 주문 : 배치 = 1 : N (지금은 1:1). `unit.order_id` 가 이음매
- 🔄 **실물 배치는 주문 없이 태어난다** — `POST /local/print` 성공 순간 `Spawn(cmd_id, contents=프리셋 part_type×1, source=ADAPTER)`. `unit.cmd_id` 가 제어 DB `print_command` 와의 **유일한 다리**. 주문 UI 는 없다(`POST /spawns` 안 만듦)
- 계보 `v_unit_lineage` — 부품 → 배치 → 주문
- 과거 이름 검색 `display_id LIKE 'P3-%'`

읽기는 M4 뷰를 얇게 감싸고, 쓰기는 **전부 이벤트 4개 + 기록 테이블**로만 간다. **`product_state` 직접 UPDATE 0건.** 정본 = `web-api/app/line/routes_read.py` · `routes_write.py` · 명세 `docs/juhee/04_API_명세/20260921_API명세.md`.

## 쓰기는 이벤트로만

```
이벤트 4개    Spawn · State · Moved · Split           → product_state 를 바꾼다 (엔진이 검증)
직접 INSERT   judgement · command_log · group_close  → 아무것도 안 바꾼다 (기록만)
```

경계가 여기다 — **위치를 바꾸는 것만 이벤트**이고, 검증이 두 벌이 되면 규칙이 갈라진다.
다만 **NG 판정만은 둘이 붙어 있다** — 판정은 기록이고 폐기함으로 가는 것은 이동이라 한 트랜잭션으로 묶는다.

🚨 상태 엔진의 거부(용량 초과 · FIFO 위반)는 **409 `ENGINE_REJECTED` 로 원문 그대로** 내려보낸다. 400 으로 뭉개지 않는다. 🔄 없는 개체·노드는 404 `NOT_FOUND`, 형식 오류는 422(`BAD_STATUS`·`BAD_REF`·`BAD_VERDICT`), `LINE_DSN` 비면 503 `LINE_MES_OFF`.

## 붙일 위치 — PG 위치와 한 몸이다

web-api 에 붙이면 그 프로세스가 PG 에 직접 커넥션을 열고, web-api 는 공장 PC 에서 돌다.
⇒ **PG 도 공장 PC 에 두는 것이 자연스럽다.** 다른 머신이면 DB 커넥션이 인터넷을 건너고,
끊기면 **관측이 아니라 제어 프로세스가 느려진다.**
🔄 **확정** — 공장 PC. 배포 순서는 `20260922_API개발_전체계획.md §10`(PG 설치 → `psql -f line_mes/schema.sql` → `topo_sync --apply` → `.env LINE_DSN`). `LINE_DSN` 이 비면 v2 전체 no-op(503 · 발행 건너뜀 · FE 목업). 접속은 `psycopg3 + psycopg_pool`(SQLAlchemy 안 씀).

🚨 비용 — web-api 가 **DBMS 3개**(SQLite + MariaDB + PG)를 보게 된다.
SQLite 로 내리는 것은 **불가**(`schema.sql` 을 먹이면 뷰 19개 중 3개만 통과, 함수는 지원 안 함),
반대 방향(v1→PG)은 기술적으로 싸지만 인스턴스 3대 이사가 걸려 **P5** 다.
