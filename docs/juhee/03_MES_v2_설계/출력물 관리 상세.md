> 🔄 **2026-09-29 현행화** — 개념은 그대로. `unit.cmd_id` 다리 · 실물 Spawn 경로 · 엔진 거부 완화(SIM 만 raise) · W4 NG 트랜잭션을 코드 기준으로 덧붙였다. 스키마 정본 = `line_mes/schema.md`.

**재공품(WIP)과 자산을 섞지 않는다.**

```
customer_order   상거래   고객 · 납기 · 출하           주문 : 배치 = 1 : N
      ↓
unit (BATCH)     생산     한 플레이트 분량 · P3-W2      배치 : 부품 = 1 : N
      ↓ Split (부품 분리 · SEP-01)
unit (PART)      개체     개별 부품 · P3-W2-S15

플레이트 = line.plate_count 숫자.   바구니·박스 = product_state.group_id 꼬리표.
```

추적 단위가 **부품 분리에서 바뀜다.** 그 앞은 배치, 그 뒤는 개별 부품이다.
부품 분리(`SEP-01`)와 서포트 제거(`SUP-01`)는 **다른 노드**다 — 같은 작업대에서 배치 단위로 단계가 바뀐다.
`splits_batch: true` 가 붙은 것은 **`SEP-01` 하나뿐**이고, 배치는 그 노드를 통과할 수 없다.

| 구간 | 추적 단위 | 이동 캐리어 | 담당 |
| --- | --- | --- | --- |
| 프린터 대기 랙 → 세척기 완료 랙 | **배치** (`unit_kind='BATCH'`) | 빌드플레이트 | 로봇암 A |
| **부품 분리 (`SEP-01`)** | ← 여기서 분해 (`Split`) | — | 작업자 |
| 부품 분리 → 서포트 제거 (`SUP-01`) | **개별 부품** | 묶음 (`group_id`) | 작업자 |
| 서포트 제거 → 경화기 | **개별 부품** | 바구니 (한 번에 여러 개) | 작업자 |
| 경화기 → 치수검사 → 완료 랙 | **개별 부품** | 부품 하나씩 | 작업자 / 로봇암 B |

작업자가 플레이트에서 출력물을 **떼어내고**(분리), 떼어낸 부품을 **하나씩 다듬고 판정**한다(서포트).
그 뒤 바구니째 경화하고 꺼내 **하나씩 치수검사**한다.

# 주문 — 라인이 왜 도는가

| 항목 | 내용 |
| --- | --- |
| 테이블 | `customer_order` · `order_line`. 고객은 문자열 — 반복 주문이 쌓이면 마스터로 |
| 🔄 현행 | **주문 UI·`POST /spawns` 는 만들지 않았다.** 실물 배치는 `POST /local/print` 성공 순간 `web-api/app/local/line_publish.py` 가 `Spawn(cmd_id, contents=프리셋 part_type × 1, source=ADAPTER, order_id 없음)` 으로 만든다. 주문은 시뮬레이터(`SIM-0001…`)에서만 생긴다 |
| 관리 범위 | 고객 · 납기 · 수량 · 출하 |
| 상태 | `OPEN` → `IN_PROGRESS`(첫 투입 시 자동) → `SHIPPED` / `CANCELLED` |
| 배치와의 관계 | **한 플레이트에 한 주문만** 올린다. 지금은 주문 1 = 배치 1 이지만, 수량이 커지면 여러 장으로.
`unit.order_id` 가 이음매 — 배치 여럿이 같은 `order_id` 를 가리키면 된다 |
| 투입 | `Spawn.contents` 를 비우면 `order_line` 을 그대로 배치 내용물로 복사 |

`v_order_progress` — 납기까지 남은 시간, 주문/생산/폐기/완료 수량을 한 줄로.
**"납기 임박한 주문이 어디 걸려 있나"** — 실무에서 설비 가동률보다 자주 묻는 질문이다.

# 배치 — 한 플레이트 분량

한 번의 출력으로 나온 출력물 묶음. **빌드플레이트 자체가 아니다** — 판은 재사용 자산이다.

| 항목 | 내용 |
| --- | --- |
| 테이블 | `unit` (`unit_kind = 'BATCH'`) — 개체당 1행 |
| 식별자 | `unit_id` (UUID, 불변) · `order_id` · `display_id` · 🔄 **`cmd_id`** — 제어 DB `print_command.cmd_id` 와의 유일한 다리(BATCH 에만 · 수동·시뮬은 NULL · FK 없음). `GET /local/automation/commands` 가 이것으로 `line_tracked` 를 낸다 |
| 내용물 | `unit_content(unit_id, part_no, qty, qty_scrapped)` — 뭐가 몇 개 실렸나 |
| 혼재 | 한 배치에 파트가 섞일 수 있다 (같은 주문 안에서, 보통 2~3종) |
| 수명 | 투입 → 부품 분리에서 **소비**(`consumed_at`). 이후 이력으로만 남는다 |
- 배치의 `display_id` 는 `P3-W2` 까지다. 프린팅·세척이 배치 단위라서다
- 🔄 실물 Spawn 이 실패하면(PG 없음 · 시리얼 미등록) 출력은 그대로 진행되고 `print_jobs.error_message = LINE_UNTRACKED: …` 만 남는다. `HistoryPage` 가 주황 "라인 미등록" 으로 표시 — **관측이 제어를 막지 않는다**
- `unit` 에 `part_no` 컬럼을 두지 않는다 — 혼재 배치에서 가리킬 대상이 없다

# 캐리어 — 숫자와 꼬리표

관측 시스템은 실물을 모방하지 않는다. 캐리어는 개체가 아니다.

| 캐리어 | 표현 | 왜 |
| --- | --- | --- |
| 빌드플레이트 | `line.plate_count` — **숫자** | 보유 수 = 동시 진행 배치 수 상한. 넘으면 투입 거부.
어느 판이 어디 있는지는 실물이 알아서 강제한다 |
| 바구니 · 트레이 · OK박스 | `product_state.group_id` — **꼬리표** | "이 부품들이 같이 간다"만 알면 된다. 바구니의 정체는 모른다.
`Moved(group_id)` 로 묶음째, `Moved(unit_id, join_group)` 로 합류 |
- `v_plate_usage` — 프린터가 4대여도 플레이트가 3장이면 3대까지만 도는 것이 데이터로 강제된다
- 검증 — 보유 2장에 3번째 투입 거부, 분해 후 1/2 로 자동 복귀 (복귀 로직 없이)
- 🔄 **거부는 `source=SIM` 일 때만 raise** (`state_engine.py:111-139` · 9/22). 실물 소스(`ADAPTER`·`ROBOT`·`CAMERA`·`MANUAL`)는 플레이트 소진·정원 초과여도 경고만 남기고 unit 을 만든다 — 관측이 제어를 판정하지 않는다. `plate_count` 는 두 라인 다 6

# 개별 부품

**파트넘버와 공정번호는 부품의 속성이다.** 배치는 그걸 묶어 나른 단위일 뿐이다.

| 항목 | 내용 |
| --- | --- |
| 테이블 | `unit` (`unit_kind = 'PART'`) — **부품당 1행** |
| 식별자 | `unit_id` (UUID) — 부품마다 고유 |
| 파트넘버 | `unit_content` 에 한 행, `qty = 1` — "무슨 파트인가"의 유일한 답 |
| 공정번호 | `unit.display_id` — **부품 자신의 컬럼** |
| 주문 | `unit.order_id` — 부모 배치에서 물려받는다 |
| 출생 | `parent_unit_id` — 어느 배치에서 나왔나 |
| 탄생 | `Split` 이벤트. **부품 분리(`SEP-01`)** 에서 배치 1 → 부품 N. **NG 는 `outputs` 에 넣지 않고 `part_scrap` 으로** — `unit` 이 생기지 않는다 |

## 파트넘버 (`part_no`)

- 개체가 아니라 **품종** 식별자. 같은 모양이면 값을 공유한다
- `part` 마스터 — `name`, `revision`, `cad_ref`, `attrs jsonb` (공차 등)
- 분해 전에는 `unit_content` 에 **수량으로**, 분해 후에는 **한 행 `qty=1`** 로 개별화된다

## 공정번호 (`display_id`)

최종적으로 **부품의 것**이다. 앞부분(`P`·`W`)은 소속 배치에서 물려받는다.

```
U-a1b2c3d4              투입 직후 (임시)
P3                      프린터 완료          ┐ 배치 구간
P3-W2                   세척 완료            ┘
P3-W2-S15               부품 분리 = 분해     ← 여기서 부품이 태어난다 (SEP-01)
P3-W2-S15-C102          경화 완료            ┐ 부품 구간
P3-W2-S15-C102-D98      치수검사 완료         │
P3-W2-S15-C102-D98-B45  빔피킹 완료          ┘
```

- 접두: `P` 프린터 · `W` 세척 · `S` **부품 분리** · `C` 경화 · `D` 치수검사 · `B` 빔피킹
서포트 제거(`SUP-01`)는 **채번하지 않는다** — `id_prefix` 가 없다. 부품을 다듬고 판정할 뿐이다
- 순번은 **리셋 없음** → 전역 유니크
- 부품마다 `C`·`D`·`B` 번호가 따로 붙는다
- **과거 이름 검색** — `display_id = 'P3' OR LIKE 'P3-%'`
- 와이어프레임의 `PT-2026-0412-01`(주문 기반)도 `order_id + 순번` 로 파생 가능 — 어느 걸 기본으로 보여줄지는 작업자에게 확인

## 채번 규칙

- 채번 지점 = M3a **단 하나**. `_relocate()` 에서만
- 조건 ① `from_node` 에서 `status == 'DONE'` 이었을 것 (가공했는가)
- 조건 ② `unit.named_at != from_node` — 그 노드에서 **아직 이름을 받지 않았을 것**.
이 조건이 없으면 분해로 태어난 부품이 부품 분리대를 떠날 때 `P1-W1-S1-S12` 처럼 S 를 두 번 받는다 — 실제로 겪음
- `edge_kind` 로 판별하면 **틀린다** — 되주차 경로에서도 세척기를 떠나면 `W` 가 붙어야 한다

## 계보 추적

`v_unit_lineage` — 부품 → 배치 → 주문.

```
P1-W1-S1-C1-D1-B1  ←  배치 P1-W1  ←  주문 ORD-2026-0412
```

# 판정 (`judgement`)

서포트제거의 OK/NG 와 치수검사의 측정값이 **같은 개념** — "어느 부품을 어느 공정에서 누가 어떻게 판정했나."

- `verdict` OK/NG/RETEST · `value` jsonb (`{"measured": 12.03, "tol": 0.15}`) · `note` · `source` AUTO/MANUAL
- **append only.** 사람이 자동 판정을 뒤집으면 새 행 → 이력이 남는다. 유효 판정은 `v_latest_judgement`
- 검증 — `P1-W1-S2-C2-D2` 자동 NG → 사람 OK 뒤집기. 이력 `[NG AUTO, OK MANUAL]`, 유효 = OK
- 🔄 화면 = `PartJudgeScreen.tsx`(W4 `POST /judgements`) · 측정란은 `node.attrs.measure` 가 있을 때만(치수검사 `INS-01` = `height_mm`) · 자동 판정(`source=AUTO`) 생산자는 아직 없다 — 치수검사 광학계 미도착

# 불량 처리 — 단계별로 나온다

프린팅 후 · 세척 후 · 분리 후 · 서포트 후 · 경화 후 · 빔피킹 후 — 어느 공정에서든.

| 시점 | 대상 | 방식 |
| --- | --- | --- |
| 분해 전 (프린팅·세척·부품 분리) | 배치의 내용물 | `unit_content.qty_scrapped` 누적. NG 부품은 `unit` 이 생기지 않는다 |
| 분해 후 (서포트·경화·검사·빔피킹) | 부품 개체 | `EXIT-SCRAP` 으로 이동 (`edge_kind: EXIT`). 🔄 W4 `NG` 가 **같은 트랜잭션**에서 route 의 EXIT 엣지 목적지로 `Moved` — EXIT 엣지가 없는 라인(현 `RESIN-1-ASIS`)에선 409 |
- 사유는 양쪽 모두 `part_scrap` 에. **INSERT 한 문장** — 트리거가 `qty_scrapped` 를 맞춘다. 초과 폐기는 CHECK 가 막는다
- `qty` 는 **투입 수량으로 고정** — 원본을 보존해야 수율을 계산할 수 있다
- `v_scrap_summary` — 공정별·파트별·사유별 불량률

# 혼재 배치

- `v_unit_content.single_part` — 혼재면 `NULL`. 집계에서 혼재를 걸러내는 조건
- **파트별 사이클타임 집계는 `single_part IS NOT NULL` 만** (분해 전 구간). 혼재분의 세척 10분을 파트별로 나눌 근거가 없다
- **생산량 = 부품 수 · 라인 속도 = 배치 수** — KPI에 둘 다

# 묶음 이동 (`group_id`)

- `Moved(group_id=...)` — **이동 1건으로 같은 꼬리표의 부품 전부** (바구니째 경화)
- `Moved(unit_id=...)` — 개별 이동. 꺼내면 꼬리표가 끊긴다
- `Moved(unit_id=..., join_group=...)` — 개별 이동인데 도착지에서 새 묶음에 합류 (OK 박스 12개 적재). 박스 번호는 `id_counter('BOX')`
- 검증 — 묶음 이동 1건으로 5개 이동, 경화기 점유 5/12, 검사로 하나씩 빠짐
