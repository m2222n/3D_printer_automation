## 1. 🧭 무엇을 하는 일인가 (5줄 요약)

카메라는 *"부품이 카메라 기준 어디 있는지"* 를 안다.
로봇은 *"자기 기준 어디로 가야 하는지"* 만 안다.
**둘 사이 변환을 구하는 것**이 hand-eye다.

⭐ **3점법** = 같은 물리적 3점을 **①카메라로 보고 ②로봇으로 찍어서** 변환을 푼다.
근거 = `rodi_script_api_manual_ko.pdf:114` — *"**3 점 좌표계 정의는 워크 좌표계 설정의
표준적인 방법**"*, 사용 시나리오에 *"비전 보정에서 캘리브레이션 좌표 결정"* 명시.

### ⚠️ 왜 기존 `hand_eye_calibration.py`(1155줄)를 안 쓰는가

**버리지 않는다. 다만 지금 목적에 맞지 않는다.**

| | 기존 파일 | 이번 |
|---|---|---|
| 전제 | **eye-in-hand**(카메라를 팔에) | 🎯 **고정 거치**(WEEK_PLAN:22 *"고정 거치로 먼저"*) |
| 방법 | 체커보드 + `cv2.calibrateHandEye()` | **로봇으로 3~6점 찍기** |
| 현장 시간 | **로봇 자세 15개 티칭·촬영** | **점 3~6개** |
| 로봇 포즈 | 매 촬영마다 필요(Modbus 전제) | **불필요**(카메라가 안 움직인다) |

⇒ 📌 **eye-in-hand로 전환할 때 기존 파일이 그대로 살아난다.** 이 카드는 **그 앞 단계**다.

## 2. 🔧 준비물

| | 항목 | 비고 |
|---|---|---|
| ☐ | **뾰족한 것을 로봇 TCP에 장착** | 티칭 정밀도가 결과 정밀도다. 그리퍼 손가락 끝이라도 된다 |
| ☐ | **점 표식 4~6개** | 빈 바닥에 붙일 것(테이프에 십자 표시 등). ⭐**카메라와 로봇 양쪽에서 같은 점을 찍어야 한다** |
| ☐ | Blaze 고정 거치 | 🚨 **캘리브 후 절대 움직이면 안 된다**(움직이면 전부 무효) |
| ☐ | `work_coord_3point.py` | 6000 → IPC 이식 확인 |

### 🚨 점을 어디에 붙이나 — 여기서 정밀도가 갈린다

```
        빈(택배 상자) 위에서 본 그림

     P4 ●───────────────● P3
        │               │        ⭐ 규칙 3개
        │   (부품 영역)  │        ① 넓게 벌린다 (최소 50mm, 가능하면 150mm+)
        │               │        ② 한 직선에 놓지 않는다
     P1 ●───────────────● P2     ③ 부품이 놓이는 영역을 감싼다
        └── X축 방향 ──→
```

⭐ **4점 이상 권장.** 3점이면 점 하나가 1mm 틀려도 **조용히 기울어진 좌표계**가 나온다.
4점 이상이면 **잔차가 나와서 "티칭이 잘못됐다"를 즉시 안다.**
📌 코드가 이것을 강제한다 — 잔차 **5mm 초과면 예외를 던지고 좌표를 보내지 않는다.**


☐ P1 = `[      ,       ,       ]`
☐ P2 = `[      ,       ,       ]`
☐ P3 = `[      ,       ,       ]`
☐ P4 = `[      ,       ,       ]`

🚨 **적을 때 단위 확인** — 로봇은 **mm**다. 우리 코드도 mm로 통일했다

각 표식의 **depth 좌표(x,y,z mm)** 를 읽는다.
⭐ 표식 중심 픽셀의 depth + intrinsic으로 3D를 만든다(7/28 Blaze intrinsic RMS 0.213px 확보됨).

☐ C1 = `[      ,       ,       ]`
☐ C2 = `[      ,       ,       ]`
☐ C3 = `[      ,       ,       ]`
☐ C4 = `[      ,       ,       ]`

### 🅒 변환 풀기 (즉시 판정된다)

```python
import numpy as np
from src.acquisition.work_coord_3point import solve_rigid_transform, save_calibration

cam = np.array([C1, C2, C3, C4], dtype=float)   # 카메라에서 본 점 [mm]
rob = np.array([P1, P2, P3, P4], dtype=float)   # 로봇으로 찍은 점 [mm]

r = solve_rigid_transform(cam, rob)             # 🚨 실패하면 예외를 던진다
print(r.report())
save_calibration(r, "config/work_coord_0829.json",
                 meta={"date": "2026-08-29", "camera": "blaze_fixed", "n_points": 4})
```

### ✅ 판정 기준 — **현장에서 고민하지 않는다**

| 지표 | 🟢 통과 | 🔴 다시 티칭 |
|---|---|---|
| **RMS 잔차** | **< 3mm** | ≥ 5mm (코드가 예외) |
| 최대 점 오차 | < 5mm | ≥ 5mm |
| **스케일 비** | **0.98 ~ 1.02** | 벗어나면 **단위 실수/점 대응 어긋남** |

⭐ **잔차 3~5mm 구간**은 통과하지만 *"부품 크기 대비 큰가"* 를 본다 —
그리퍼 벌림 여유가 **10mm**(`GRASP_SAFETY_MARGIN_MM`)이므로 **잔차 5mm는 여유의 절반**을 먹는다.

## 5. 🔗 인식 → 파지로 잇기 (9/1~ P4)

```
Blaze depth ─→ depth_track 추론 ─→ 6요소(x,y,z,edge,angle,label)
                                          │
                                   [카메라 좌표 mm]
                                          ↓
                          camera_point_to_robot(T, xyz)   ← 🆕 이 카드
                                          ↓
                                   [로봇 좌표 mm]
                                          ↓
                          pick_socket_server (검증 후 전송)
                                          ↓
                                   로봇 Rodi-Script
```

⭐ **`pick_socket_server.py`가 이미 3단계 안전 절차를 갖고 있다** — 그 순서를 지킨다:

| 단계 | `--mode` | 내용 |
|---|---|---|
| 1 | `handshake` | 빈 배열. TCP 왕복만. **로봇 안 움직임** |
| 2 | `teach` | 티칭으로 검증된 좌표 1개. 모션 확인 |
| 3 | `vision` | 🚨 **인식 결과 — hand-eye 완료 후에만** |

🚨 **로봇 클라이언트에는 좌표 검증이 없다.** 서버가 z=3136mm(7/29 실제 버그)를 보내면
그 높이로 뻗는다 ⇒ **막을 곳이 서버뿐**이라 두 겹으로 검증한다
(`camera_point_to_robot`의 범위 검사 + `pick_encoder`).
