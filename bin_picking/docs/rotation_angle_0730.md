## 1. 왜 했나 — 조사가 가정을 뒤집었다

7/29 6요소 출력은 `angle=0.0` 고정이었다(`notes`에 `angle=0_mask_not_saved`).
**0은 "회전 없음"이 아니라 "모른다"** 는 뜻이다.

착수 전 판단: 각도는 북극성 기준 **3순위**다(1=실환경 인식 검증, 2=hand-eye 캘리브).
그래서 "부품이 대부분 정사각형이면 건너뛰고 공장 준비에 시간을 쓰자"는 가설을 세우고
**27종 종횡비를 실측**했다 (`tests/survey_rotation_asymmetry.py`).

### 🔴 결과 = 가설이 반대로 뒤집혔다

| 판정 | 종수 | 검출 건수 |
|---|---|---|
| 🔴 각도 필수 (종횡비 >1.5) | **22종 (81%)** | **654/801 (82%)** |
| 🟡 애매 (1.15~1.5) | 4종 | |
| 🟢 각도 불필요 (<1.15) | **1종 (4%)** | |

극단값: `top_inner_sheet` **19.0:1**(19×1mm) / `17_mks_holder` **11.9:1**(131×11mm) /
`08_r_guide_a` **6.7:1**(271×41mm, 최대 부품).
각도 없이 집을 수 있는 것은 `brkt_switch`(20.4×20.0mm) **1종뿐**.

⭐ **결론 = 각도는 "있으면 좋은 것"이 아니라 "없으면 82%를 못 집는 것"**. 후순위 판단을 정정.
(순위 자체는 인식 검증·hand-eye가 여전히 앞 — 다만 그 둘은 로봇·새 촬영이 필요해 재택 불가)

## 2. 🚨 왜 모델이 각도를 안 주나 — KAIST 설계와의 관계

**모델이 각도를 예측하지 않는다. 설계상 못 한다.**

근거: `model/cad_pointcloud_dataset.py:48 _random_z_rotation` — CAD 포인트클라우드를
**무작위로 돌려서** 학습시키는 증강. 목적은 **회전 불변(rotation invariant)**,
즉 "어느 방향으로 놓여 있어도 같은 부품으로 인식".

⭐ KAIST 프로젝트 지표는 **종류 식별 F1**이었고 회전 불변이 그 지표를 올린다 = **맞는 설계**.
🔴 그런데 **로봇에게 필요한 각도를 일부러 버린 것**이다. 종류를 맞혀도 방향을 모르면 못 집는다.

→ **모델을 재학습하지 않고 마스크 모양에서 기하학적으로 복구**한다(모델 밖 우회로).
   재학습·재추론 불필요 = CPU로 가능.

## 3. 원인은 단순했다 — 마스크를 저장 직전에 버리고 있었다

`eval_real_depth_vq_detector.py:181`에서 마스크가 이미 계산된다(`prediction_masks_np`).
그런데 **500행에서 버린다**:
```python
clean_inf = {k: v for k, v in inf.items() if k != "masks"}
```
그래서 7/29에 bbox(축정렬 네모)만 갖고 작업해야 했고, 네모는 각도를 줄 수 없다.

## 4. 한 것

### `src/pipeline/mask_to_angle.py` (신설)
`cv2.minAreaRect`로 마스크의 **최소 회전 사각형**을 구해 각도·회전 edge를 낸다.
- ⭐ 각도 규약은 `yolo_track/pipeline/detect_and_output.py:299-307`과 **동일**하게 맞춤
  (두 트랙이 다른 규약을 쓰면 로봇 쪽에서 혼동)
- ⚠️ 마스크 전체는 저장하지 않는다(100장×수십개면 무거움) — **각도·OBB 4점만** 남긴다
- ⭐ **`angle_reliable` 플래그 신설** = 각도를 믿을 수 있는지 두 조건으로 판정
  - 종횡비 < 1.15 → 거의 정사각형이라 **각도가 물리적으로 무의미**
  - fill < 0.45 → ToF 구멍으로 **마스크가 깨진 것** 의심

### `eval_real_depth_vq_detector.py` (수정, 최소 침습)
마스크를 버리기 **전에** 각도를 뽑아 예측에 심는다. `--no_angle`로 끌 수 있다.
- ⚠️ **crop·resize 역변환을 반드시 적용** — 빼먹으면 좌표가 밀린다(7/29에 141px 밀림 경험)
- ⚠️ 각도 산출 실패가 **평가 자체를 죽이지 않게** try/except (F1 재현이 주 목적)

### `src/pipeline/depth_track_to_6elements.py` (수정)
`angle_deg`가 있으면 쓰고, 없으면(옛 예측 JSON) 종전 fallback으로 떨어진다.
`angle_reliable`·`obb_aspect`를 6요소 출력에 함께 실어 로봇이 걸러쓸 수 있게 했다.

### ✅ 회귀 없음 확정 — 인식 지표 15개 전부 소수점까지 동일
```
tp 685 / fp 116 / fn 188        (7/29과 완전 동일)

```
⭐ **각도 추가가 인식 성능을 전혀 건드리지 않았다** = 순수 추가 기능.
   (마스크를 버리기 전에 읽기만 하고 예측·평가 경로는 손대지 않았기 때문)

### ⭐ 각도 분포 = 버그가 아님을 보이는 증거
```
0~180도 골고루: {0:85, 30:70, 60:81, 90:135, 120:58, 150:73, 180:78}
```
부품이 빈에 무작위 방향으로 놓이므로 **각도도 퍼져야 정상**. 한쪽으로 쏠렸다면 변환 버그였다.
- 90° 근처(99건)가 다소 높은 것은 **정사각형에 가까운 부품이 긴축 보정(`w<h`→+90°) 경계로
  몰리는 정상 현상**. 그 구간 종횡비 중앙 1.40(기타 1.54)이고 71%만 reliable로 표시됨
  = 플래그가 제 역할을 함. 특정 부품 편중도 없음(5종에 분산).
- ⭐ **독립 교차검증**: STL 기하 조사의 "각도 유의미 81%" vs 실측 마스크 `reliable` 80.6%
  → 서로 다른 두 경로가 같은 답.

## 6. ⚠️ 남은 한계 (로봇 연결 전 알아야 할 것)

- **겉모양 방향 ≠ 파지 방향**. 실제 파지는 `grasp_database.yaml`의 `approach_axis`·
  `grasp_center`와 결합해야 하고, 그 값들은 "STL bbox 추정치, **로봇 티칭 후 실측 교정
  필요**"로 명시돼 있다(`grasp_database.yaml:22-23`).
- **180° 모호성** — 길쭉한 부품의 θ와 θ+180°는 구분 안 됨. 평행 그리퍼는 보통 무관하나
  (양쪽에서 물므로), **앞뒤 구분이 필요한 부품에는 부족**.
- **`reliable=False`도 값은 나온다** — 정사각형에서 `minAreaRect`가 임의 각도를 주기 때문.
  로봇 쪽에서 **플래그를 반드시 보고 걸러야** 한다.
- ⏸️ 좌표계는 여전히 **Blaze 카메라 프레임**. hand-eye 미착수 = 로봇 Base 변환은 통째로 빔.
