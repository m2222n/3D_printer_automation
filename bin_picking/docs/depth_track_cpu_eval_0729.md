## 결과 — 실측 100장 (6/26 촬영분)

| 지표 | 값 |
|---|---|
| **F1 (micro)** | **0.8184** |
| precision / recall | 0.8552 / 0.7847 |
| mask IoU (macro) | 0.8703 |
| TP / FP / FN | 685 / 116 / 188 |
| 장면 수 | 100 |

평가 조건 = 발표와 동일하게 맞춤: `iou 0.25 / score 0.45 / nms 0.5(mask) / center_crop 1/6,5/6 / depth_keep 0.40~0.60 / bbox_source mask`

## ⚠️ 이 0.818을 발표 0.684와 나란히 놓으면 안 된다 — 시험지가 다르다

| | 발표 test100 (0.684) | 오늘 (0.818) |
|---|---|---|
| 평가 대상 | **test split 102장**(학습에 안 쓴 것) | **`real_capture100` 100장 전체** |
| 학습 포함 여부 | ❌ 미포함(hold-out) | ⚠️ **일부가 train/val에 포함됐을 가능성** |
| 의미 | 일반화 성능 | **재현·파이프라인 동작 확인** |

`resplit_test100.py:2,12-14`가 실측 **200장**을 4:1:5로 나눴고, 층화 기준이 **`shot`/`shot2` 두 출처**다.
즉 학습셋 E200 = `real_capture100`(6/26, shot) + `blaze_capture100_v2`(7/6, shot2) **통합**이며,
오늘 평가한 100장은 그중 한 세션 **전량**이다 → train 80장 중 일부가 여기 섞여 있다.

⭐ **그래서 0.818이 0.684보다 높은 것은 성능 향상이 아니라 학습 데이터가 섞인 결과로 보는 게 맞다.**
(발표 때 test40에서 나온 0.818과 수치가 우연히 같은데, **별개 조건**이다 — 혼동 주의)

## 🚨 P0 #1의 원래 질문은 아직 답이 없다

격차 분석의 우려는 이것이었다:
> F1 0.684는 정제된 실측 100장(특정 세션·labelme 정성 라벨)으로 낸 값.
> 세척기 분류가 같은세션 0.982 → **cross-session 0.34~0.70 폭락**한 전례가 있는데 depth_track엔 미검증.

**오늘 돌린 것은 바로 그 "정제된 100장"이다.** 따라서 재현 검증이지 cross-session 검증이 아니다.

⚠️ 게다가 **가진 실측 2세션(6/26·7/6)이 둘 다 학습에 들어갔다** → 리포 안의 데이터로는
cross-session 검증이 **원리상 불가능**하다. 진짜 검증엔 **새 세션 촬영이 필요**하다.

### 그래도 오늘 얻은 것

1. ✅ **파이프라인이 6000에서 돈다** — GPU·A100 없이 추론 가능(CPU 5분/100장). 앞으로 재택에서 실험 가능.
2. ✅ **체크포인트가 온전하다** — codebook 내장 확인, 하이퍼파라미터가 `run_t100_0707.sh`와 일치.
3. ✅ **mask IoU 0.870** — 위치·분할은 학습 데이터 여부와 무관하게 안정적(발표 0.843과 근접).
4. ⚠️ **recall 0.785 < precision 0.855** — FN 188 > FP 116. **놓치는 쪽이 문제**다.
   빈피킹에선 "못 찾음"이 "잘못 찾음"보다 낫지만, 188개는 재파지 시도로 사이클 타임을 깎는다.
